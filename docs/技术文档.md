# Lucky Doctor（幸运医生）技术文档 —— 药品管理与语音播报系统

> 一句话概述：照护者用 Agent Skill 针对每一种药品 **一次性建档**（识别说明书、归纳播报文稿、药物冲突检测、语音合成/声音克隆、打包数据、生成药盒二维码贴纸），长辈用手机 App **扫码即得**药品资料与自动语音播报 —— 全流程本地推理，数据不出户，家人声音克隆更显亲切。

Skill 使用**项目内专用 venv**（`skill/.venv`），不污染系统 Python 环境：

## 2. 应用场景说明

### 2.1 创新方向

相较于之前的作品 [【Intel AI PC创新应用征文】药品说明书智能识别与语音播报系统——让老年人轻松读懂药品说明书](https://modelscope.cn/learn/6626)，本项目利用 OpenVINO 本地推理模型，把「**一次建档，长期复用**」作为核心创新：将 OCR 识别、本地大模型归纳、药品冲突检测、语音合成与 **声音克隆** 全部前移到照护者侧一次性完成，长辈侧只剩「扫码 → 听」两个动作。

### 2.2 解决的实际问题

**痛点**：初版「拍照 → 识别 → 归纳 → 语音」的流程本身是对的，但有四个绕不开的瓶颈：

1. **耗时太长**：识别 + 归纳 + 语音合成，每次数分钟甚至十几分钟
2. **全靠长辈本人**：拍照、等待、失败重试，一步都不能少
3. **重复劳动**：每次吃药都要把整条链路重跑一遍
4. **错误会放大**：文字识别认错一个字，归纳与播报跟着错

**方案**：把重活前移给照护者（建档一次），把轻活留给长辈（扫码即听）：

| 维度 | 初版 | 现在 |
|------|------|------|
| 谁来执行 | 长辈本人，全程自己操作 | 家中照护者，建档一次就够 |
| 何时跑模型 | 每次吃药都要跑一遍 | 只在建档那一次运行 |
| 长辈侧耗时 | 数十秒到数分钟，还要重试 | ≈ 0，本地查表，扫码即播 |
| 识别准确度 | 依赖当场文字识别的准确率 | 二维码解码，确定性命中 |
| 长辈的操作 | 拍照 → 等待 → 听 → 重试 | 打开 App → 扫码 → 听 |
| TTS 方案 | 通用音色合成 | 声音克隆 |

### 2.3 面向的用户群体

1. **老年人**：主要受益者，扫码即得资料与语音，无需操作模型
2. **家中照护者**：子女/家属，负责一次性建档与数据包管理
3. **社区医疗工作者**：辅助患者用药指导

## 3. 系统设计

### 3.1 总体架构

``` text
（照护者侧 · Agent Skill，PC 本地）
  药盒/说明书照片
      │
      ▼
  [1] 识别（Agent 视觉直读优先，看不清/无视觉时 OCR 兜底：PaddleOCR-VL）
      │
      ▼
  [2] 云端/本地大模型归纳（Qwen3.8-27b int4）+ 与照护者协作编辑播报文稿
      │
      ▼
  [3] 冲突检测（records.py 对比私人药库 + Agent 药理知识补充）
      │
      ▼
  [4] 语音合成 / 声音克隆（Qwen3-TTS，可用亲人参考音频）──→ audio.wav
      │
      ├──→ create_package.py ──→ 数据包 .zip（metadata + audio）──→ 手机 App 一次性导入（本地药库）
      └──→ create_sticker.py ──→ 二维码贴纸（PNG + A4 打印页）──→ 打印裁剪贴到药盒

（长辈侧 · 手机 App，全离线）          ▼
  扫码药盒贴纸 → 解码 payload → 按 id 精确命中本地药库 → 展示资料 + 自动播放语音
```

### 3.2 核心模型

| 模型 | 用途 | 精度 / 来源 | 本地实测（Ultra 9 285H / 64GB） |
|------|------|------|------|
| PaddleOCR-VL-1.5-OpenVINO | 文字识别兜底（视觉直读取不到时） | OpenVINO · ModelScope `megemini` | 本地可用 |
| Qwen3-TTS-12Hz-0.6B-Base-OpenVINO-INT8 | 语音合成 + **声音克隆** | INT8 · HuggingFace `aurora2035` | 本地可用 |
| Qwen3.8-27B-int4-ov | 归纳播报文稿、语义级药物相互作用分析 | INT4 · OpenVINO | **可加载并正确使用，但约 3 token/s，偏慢** |

### 3.3 关键设计

#### 3.3.1 二维码贴纸：确定性识别协议

贴纸二维码 payload 为一行文本，Skill 与 App 两端严格一致：

``` text
LD|1|<record_id>|<药名>
示例：LD|1|3f2c9a1e-b7d2-4c6e-9a10-8d5e2f1a4b3c|阿莫西林胶囊
```

- `LD`：应用固定前缀，非本应用二维码给出明确提示
- `1`：payload 版本
- `record_id`：与数据包 `metadata.json` 的 `id` 完全一致，App 按 id 精确命中本地药库
- **更新边界**：文案/音频小更新用 `create_package.py --id <旧id>` 复用旧 id，已贴的旧贴纸继续有效

#### 3.3.2 本地声音克隆

- 照护者提供一小段参考音频（`--ref-audio` / `--ref-text`），Base 模型在 **本地** 提取音色并合成播报语音
- 隐私：克隆与合成本地完成，家人声纹与音频样本不上传
- 体验：长辈听到的是亲人的声音，说明书变成一句叮嘱，更愿意听、也记得住
- 音色样本随时可替换、可删除，完全由用户掌控

#### 3.3.3 隐私双层设计：本地守数据，远端补智能

- **本地**：药品名、成分、用药史只写进本机文件；声纹本地克隆；识别 / 归纳 / 合成 / 克隆可全由本地模型完成；手机药库与音频仅存本机，无账号、无云端
- **远端**：需要深入药物咨询、罕见相互作用、多药方案解读时，可调用更强的远端通用大模型
- 一句话：**本地负责「不说出去」，远端负责「懂得更多」**

#### 3.3.4 私人药物助理（冲突检测）

- 维护历史药品记录（list / search / get / add / update / on / off / remove）
- **重复用药检测**：新药有效成分与历史记录比对，揪出成分重叠（如泰诺与感冒灵颗粒均含对乙酰氨基酚）
- **相互作用检测**：内置 10 条已知冲突对规则（`conflicts.json`，如阿司匹林 + 华法林 → 高危出血风险），脚本确定性判定
- 大模型按药理知识补充规则表覆盖不到的语义级相互作用
- 风险三级标注（高危 / 中危 / 提示），报告一律附免责声明

#### 3.3.5 大模型速度：本地与云端的取舍

三个模型

- PaddleOCR-VL-1.5-OpenVINO
- Qwen3-TTS-12Hz-0.6B-Base-OpenVINO-INT8
- Qwen3.8-27B-int4-ov
  
在测试机（Intel Core Ultra 9 285H / 64GB / Windows 11）上均可正常加载使用。

- **要隐私、不怕等**：用本地 `Qwen3.8-27B-int4-ov` 作为 Agent 使用的大模型，识别、归纳、合成、克隆全部不出本机
- **要速度、要更强的药理知识**：改用云端大模型，此时 OCR 与 TTS 两个模型依然留在本地，药品图片与声音样本仍不离开本机

> 说明：`Qwen3.8-27B-int4-ov` 在测试机上速度较慢且占用资源较多，实际测试约 3 token/s，因此，如果没有独立显卡环境，还是建议整个流程使用远端速度更快的模型接入。
> 
> 说明：`Qwen3-TTS-12Hz-0.6B-Base-OpenVINO-INT8` 实际使用时有可能出现杂音等情况，原因是，模型不能处理标点符号，项目中已做处理，但使用时仍需注意。另外，长文本建议分段处理然后合并，以免出现意外中断等情况。

## 5. 总结与展望

### 5.1 端侧部署心得

1. **OpenVINO + 量化让消费级硬件跑大模型成为可能**：OCR、TTS-Base（INT8）与 Qwen3（INT4）均可在无独显的普通 PC 上推理。虽然推理速度仍有不足，但已经跨过了 `不能用` 的门槛。
2. **模型按需加载**：OCR 与 TTS 采用 lazy loading，用时加载、用完释放，避免同时常驻导致内存压力。
3. **视觉直读优先、OCR 兜底**：Agent 具备视觉能力时直接读图更快；OCR 识别准确度更高，兜底保证无视觉模型时链路依然完整。
4. **跨平台零激活**：所有脚本锁定 Python 解释器的绝对路径（venv 内），Windows / macOS / Linux 统一用 `<py> scripts/xxx.py` 运行，避开 `source activate` 的平台差异。
5. **本地大模型要按需取舍**：在 Ultra 9 285H / 64GB 上，`Qwen3.8-27B-int4-ov` 能正常加载并给出正确结果，但约 3 token/s，只适合"不怕等、要隐私"的场景；OCR 与 TTS 两个小模型本地速度够用。把"归纳"这一环做成可替换（本地 or 云端），比硬扛端侧速度更务实。

### 5.2 当前局限

1. 极度模糊、字体极小的说明书，大模型识别准确度仍有上升空间
2. TTS 断句偶尔不符合自然停顿，属于模型衔接上的局限
3. 本地大模型速度较慢，建档时需要等待

### 5.3 优化方向与未来规划

从产品需求的角度出发仍可增加和优化：

- **服药提醒与用药打卡**：扫码即记录，生成依从性周报
- **效期管理**：录入有效期，临期提醒
- **多成员药箱**：一人建档，全家共享；照护者远程下发新数据包（贴纸不变）
- **更多声音**：方言与情绪语调，随场景切换
- **范式迁移**：「离线建档 → 生成贴纸 → 扫码即得」这套闭环可复用到家电说明书、食品过敏原/保质期、随身应急卡、证件票据收纳等一切「需要看懂却看不懂、需要记住却记不住」的场景

### 5.4 结语

Lucky Doctor 用「一次建档、长期复用」重构了药品说明书的获取方式：复杂留给 AI 和子女，简单留给父母。三个本地模型、一枚二维码、一个 ZIP，整条闭环不出户；既守住了数据隐私，又通过「本地 + 远端」双层设计保留了进一步咨询更强模型的能力。
